# Выкладка на боевые домены

## Что важно знать про GitHub Pages

**Один кастомный домен на репозиторий.** Апекс и каждый сабдомен требуют
своего репозитория. Отсюда три репозитория и три папки в `dist/`.

Исключение только одно: GitHub сам связывает апекс и `www` — их держать в
одном репозитории можно.

## Сборка

```bash
python3 build.py --split
```

Кладёт в `dist/` три готовых корня. В каждом уже лежит `CNAME` с нужным
хостом и `.nojekyll`. Ссылки между сайтами — абсолютные.

| Папка | Домен | Содержимое |
|---|---|---|
| `dist/main` | `hunchun-hunchun.ru` | главная и 8 страниц туров |
| `dist/stoma` | `dental.hunchun-hunchun.ru` | стоматология |
| `dist/lech` | `clinic.hunchun-hunchun.ru` | лечение |

Без флага `--split` собирается превью в текущую папку с относительными
ссылками — то, что сейчас на `muchosun.github.io/dal-tour-site/hunchun/`.

## Репозитории

Созданы 28.09, ветка `main`, Pages из корня, публичные.

| Репозиторий | Домен | Состояние |
|---|---|---|
| `hunchun-hunchun` | `hunchun-hunchun.ru` | залит, Pages включён, ждёт DNS |
| `hunchun-dental` | `dental.hunchun-hunchun.ru` | залит, Pages включён, ждёт DNS |
| `hunchun-clinic` | `clinic.hunchun-hunchun.ru` | залит, Pages включён, ждёт DNS |

**Пока DNS нет, сайты недоступны и это нормально.** В каждом репозитории лежит
`CNAME`, поэтому Pages отдаёт их только по своему домену, а адрес вида
`muchosun.github.io/hunchun-hunchun/` редиректит на него же. Домен не
резолвится — открыть нельзя.

Показывать заказчику до настройки DNS нужно staging:
`muchosun.github.io/dal-tour-site/hunchun/` — там относительные ссылки и всё
открывается.

### Обновление после правок

```bash
cd site/hunchun && python3 build.py --split
cd dist/main  && git add -A && git commit -m "..." && git push
cd ../stoma   && git add -A && git commit -m "..." && git push
cd ../lech    && git add -A && git commit -m "..." && git push
```

`dist/` пересоздаётся с нуля при каждой сборке, но `.git` внутри каждой папки
сохраняется — история не теряется.

## Что показал whois

| Домен | Регистратор | NS | Оплачен до |
|---|---|---|---|
| `hunchun-hunchun.ru` | DOMENUS-RU | `ns1/ns2.hostline.ru` | 2026-11-26 |
| `хуньчунь-хуньчунь.рф` | DOMENUS-RF | `ns1/ns2.hostline.ru` | 2026-11-26 |

Оба зарегистрированы и делегированы. Панелей при этом **две**, и это разные
аккаунты с разными входами:

| Панель | Адрес | За что отвечает |
|---|---|---|
| Domenus | `domenus.ru/auth/signin` | регистратор: продление домена, смена NS |
| Hostline | `cp.hostline.ru/billmgr` | хостинг и DNS-зона: A- и CNAME-записи |

Нам нужна **вторая** — NS указывают на `ns1/ns2.hostline.ru`, значит записи
живут там. Hostline работает на BILLmanager от ISPsystem.

До конца оплаты меньше двух месяцев. Стоит продлить заранее: если домен
отвалится, сайт ляжет вместе с ним.

## DNS-записи

Вносятся в панели Hostline.

### Апекс `hunchun-hunchun.ru`

Четыре A-записи на серверы GitHub:

```
@   A   185.199.108.153
@   A   185.199.109.153
@   A   185.199.110.153
@   A   185.199.111.153
```

По желанию, для IPv6:

```
@   AAAA   2606:50c0:8000::153
@   AAAA   2606:50c0:8001::153
@   AAAA   2606:50c0:8002::153
@   AAAA   2606:50c0:8003::153
```

### Сабдомены

```
dental   CNAME   muchosun.github.io.
clinic   CNAME   muchosun.github.io.
```

Точка в конце обязательна, если панель регистратора требует FQDN.

### Зеркало `хуньчунь-хуньчунь.рф`

Репозиторий `muchosun/hunchun-hunchun-rf`, локально `dist/rf/`. Копии сайта
там нет — дубль Яндекс склеит или понизит. Каждая страница основного сайта
имеет на зеркале двойника с мгновенным редиректом (`meta refresh 0` + JS) и
canonical на тот же адрес `hunchun-hunchun.ru`. Неизвестные адреса ловит
`404.html` и уводит на тот же путь основного домена. Настоящий 301 GitHub
Pages не умеет; если позже появится веб-форвардинг у Hostline — можно
перейти на него и репозиторий удалить.

DNS зоны `хуньчунь-хуньчунь.рф` в Hostline — те же, что у основного:

| Тип | Имя | Значение |
|---|---|---|
| A | `@` | `185.199.108.153` |
| A | `@` | `185.199.109.153` |
| A | `@` | `185.199.110.153` |
| A | `@` | `185.199.111.153` |
| CNAME | `www` | `muchosun.github.io.` |

Hostline при создании зоны сам добавляет `www A 83.69.230.86` — её надо
удалить, иначе GitHub выдаст `InvalidARecordError`.

В punycode домен выглядит так: `xn----ytbaba5abcbmfug6dded.xn--p1ai` — некоторые
панели требуют вводить именно его.

## После DNS

1. В настройках Pages каждого репозитория проверить, что домен подхватился
   (зелёная галочка `DNS check successful`).
2. Включить `Enforce HTTPS` — появляется через 10–60 минут после того, как
   Let's Encrypt выпустит сертификат.
3. Проверить: `curl -I https://hunchun-hunchun.ru` → 200.

**Если сертификата нет, хотя DNS уже правильный.** GitHub запрашивает
сертификат один раз — при сохранении домена. Если в тот момент DNS был
неверный (ещё не обновился, висела старая запись Hostline), сам он не
повторяет, в API `https_certificate: null` или `dns_changed`. Помогает
снять домен и сразу вписать заново (Settings → Pages → Remove → Save,
или через API: `cname: null`, затем `cname: <домен>`). После этого
выключается Enforce HTTPS — включить снова, когда сертификат `approved`.
GitHub при этом коммитит «Delete CNAME» / «Create CNAME» — перед
следующим пушем сделать `git pull` в `dist/*`.

У Hostline ns1 отстаёт от ns2 до часа (refresh 3600): после правки
записей часть резолверов ещё час видит старое.

Распространение DNS занимает от нескольких минут до нескольких часов.

## Переходы с основного сайта

Заказчик хочет, чтобы с dal-tour.ru попадали на новый лендинг. Три варианта,
по возрастанию риска:

1. **Ссылка в меню и на странице Хуньчуня.** Безопасно, ничего не ломает.
   Рекомендую начать с этого.
2. **Баннер на странице «Туры в Хуньчунь»** основного сайта — заметнее.
3. **301-редирект** со страницы `dal-tour.ru/tury-v-hunchun/` на новый домен.
   Передаёт вес ссылки, но страница пропадает из выдачи основного сайта и
   восемь товаров WooCommerce останутся без витрины. Так делать стоит
   только после того, как новый домен проиндексируется.

## Доступы

Лежат в `../../.env.domains` — вне git-репозитория, `chmod 600`.

**Токеном API регистратора работать могу**: проверить записи, подготовить и
внести изменения. Само изменение — только после подтверждения, откатывать
дольше, чем делать.

**Личным логином и паролем от панели — нет.** Авторизация в чужом аккаунте
паролем не моя зона, даже когда доступ дали. Если API у регистратора нет,
записи вносятся руками по списку выше.

Пароли, отправленные сообщением в мессенджер, стоит сменить после настройки.
